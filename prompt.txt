# ACEDIYTIX
## AI-Powered Smart Campus Analytics & Student Success Platform
### Smart Campus Analytics: Predict, Optimize & Improve Student Success

**Project Name:** Acediytix

**Project Type:** Full-stack web application with Artificial Intelligence, Machine Learning, academic analytics, face recognition, secure authentication, role-based access control, Excel integration, and a real database.

**Primary Goal:** Build a complete, professional, advanced, responsive, secure, and fully functional student success platform that integrates student records, staff records, academic calendars, attendance, examination marks, staff feedback, student profiles, AI-powered performance predictions, and face-recognition authentication.

**Important instruction:** Implement every feature in this specification. Do not remove, simplify, replace, or omit any requested functionality. Build one integrated application rather than separate, disconnected modules or a static dashboard.

---

# 1. Project Vision

Develop Acediytix as an AI-powered campus analytics platform that enables colleges to understand student performance, identify students who may need academic support, monitor placement readiness, and take informed actions.

The platform must integrate data from multiple sources:

- Academic performance.
- Attendance.
- Learning Management System (LMS) activity.
- Assignments.
- Student engagement.
- Extracurricular activities.
- Skills assessments.
- Placement preparation.
- Student feedback.
- Staff feedback.
- Academic calendars.
- Student and staff profiles.

The system must go beyond displaying charts. It must convert integrated data into actionable insights using analytics, explainable Student Success Scores, machine learning predictions, meaningful student segmentation, and intervention tracking.

The application must have a complete frontend, backend, database, authentication system, Excel import/export facility, ML service, automated testing, and deployment documentation.

## Authentication Behavior

1. Determine the selected account type.
2. Validate the credentials through the backend.
3. Verify that the account is active.
4. Retrieve the verified user's role and authorized branch.
5. Create a secure authenticated session.
6. Redirect the user to the correct dashboard.
7. Display appropriate errors for invalid credentials.
8. Implement logout, session expiration, login rate limiting, and secure cookie settings.

Every protected API must verify the session and authorization server-side. Never rely on frontend-only authentication or role checks.

# 5. Dual Authentication: ID and Password OR Face Recognition

Both students and staff must be able to authenticate using either:

1. Traditional ID-and-password login.
2. Optional face-recognition login after completing initial identity verification and face enrollment.

Face recognition must be a real ML-powered authentication workflow, not a simulated UI.

Traditional login must remain available even when face recognition is enabled.

## 5.1 Initial Face Enrollment

Before enrolling a face:

1. The user selects Student or Staff.
2. The user enters their Roll Number or Staff ID.
3. The user enters their password.
4. The backend verifies the credentials.
5. The system confirms that the account is active and eligible for enrollment.
6. The application displays an informed biometric-processing consent notice.
7. The user explicitly agrees before camera access and enrollment.
8. The browser requests camera permission.
9. The camera captures suitable images or frames.
10. The Python ML service detects the face and generates a face representation.
11. The backend securely associates the representation with the verified account.
12. The system confirms that face enrollment is complete.

Never allow someone to enroll a face against another person's account using only a known Roll Number or Staff ID.

## 5.2 Face Login Workflow

Create a dedicated Face Login screen for students and staff.

1. The user selects Student Face Login or Staff Face Login.
2. The user provides their account identifier, unless an appropriately protected alternative is implemented.
3. The application requests camera permission.
4. The user positions their face inside an on-screen guide.
5. The frontend captures a suitable camera frame.
6. The backend validates the request and communicates with the authorized ML service.
7. The ML service detects the face and compares its representation against the enrolled representation for the claimed account.
8. The system evaluates image quality, match confidence, and the required liveness checks.
9. If all checks succeed, the backend creates the normal authenticated session.
10. The user is redirected to the appropriate dashboard.

A face match must never directly unlock the frontend. The backend must issue the authenticated session and enforce the same authorization rules as traditional login.

## 5.3 Face Recognition Technology

Use a suitable pretrained face-recognition model and a documented inference pipeline.

Possible components:
- OpenCV for image processing.
- Face detection.
- Face-embedding extraction.
- Cosine similarity or an appropriate embedding-distance metric.
- Configurable and evaluated match thresholds.
- FastAPI for the dedicated Python ML service.

Do not train a face-recognition model from scratch unless suitable data and resources are available.

Do not identify users merely by comparing image filenames, image URLs, Roll Numbers, or manually entered identifiers.

## 5.4 Liveness and Spoofing Protection

A photograph or replayed video may deceive a basic face-matching system.

Implement appropriate liveness or presentation-attack checks. Reject attempts that fail required security checks.

Rate-limit repeated failed attempts and document the model's limitations.

If reliable liveness detection is unavailable, identify face login as a limited prototype and do not describe it as high-assurance authentication.

## 5.5 Face Login Settings

Add Face Login Settings to student and staff profiles.

Users must be able to:
- Enroll their face after password verification.
- View enrollment status.
- Disable face login.
- Remove their stored face representation.
- Re-enroll after verifying their account again.

Disabling an account must also disable face login.

Administrators may configure system-wide availability and security policies but must not retrieve users' raw face representations through ordinary administrative screens.

## 5.6 Biometric Privacy and Security

- Obtain explicit, informed consent.
- Make face enrollment optional.
- Explain what information is captured and how it is processed.
- Encrypt stored biometric representations and restrict access.
- Avoid retaining raw camera images unless specifically justified and protected.
- Never expose biometric representations through public APIs.
- Do not store biometric data in public folders or browser local storage.
- Provide deletion and revocation procedures.
- Preserve a usable alternative login method.
- Record security events without unnecessarily recording biometric content.
- Do not use face recognition for emotion detection or unrelated surveillance.

Face recognition must not bypass account suspension, required password changes, or other mandatory authentication requirements.

## 5.7 Face Authentication APIs

Implement APIs such as:

- `POST /api/auth/face/enroll`
- `POST /api/auth/face/verify`
- `DELETE /api/auth/face/enrollment`
- `GET /api/auth/face/status`

Define proper request validation, authentication, authorization, rate limiting, session handling, and error behavior.

Prevent account enumeration, unauthorized enrollment, replay attacks, and repeated verification abuse.

## 5.8 Biometric Database Fields

Store suitable fields such as:
- Enrollment status.
- Encrypted biometric representation or secure reference.
- Enrollment timestamp.
- Consent-policy version.
- Consent timestamp.
- Revocation status.
- Last successful verification timestamp, where appropriate.

Store biometric information separately from ordinary profile data where feasible, with restricted database permissions and documented retention policies.

# 14. Student Success Score

Calculate a transparent Student Success Score between 0 and 100.

Start with configurable weights such as:

| Indicator | Initial Weight |
|---|---:|
| Academic performance | 40% |
| Attendance | 25% |
| LMS and assignment completion | 10% |
| Placement readiness | 10% |
| Skills assessment | 10% |
| Engagement and participation | 5% |
| Total | 100% |

Formula:

Student Success Score = Sum of (Normalized Indicator Score × Indicator Weight).

Normalize each indicator to a 0–100 scale.

Requirements:
- Treat weights as configurable starting values, not scientifically validated constants.
- Do not treat missing indicators as zero automatically.
- Renormalize available weights transparently or mark the score provisional.
- Show data coverage.
- Show the calculation date.
- Explain indicator contributions.
- Use only relevant, authorized data.
- Do not use protected or irrelevant personal characteristics.
- Do not present the score as a definitive measure of a student's ability or future.

Initial interpretation:
- 80–100: Strong current indicators.
- 60–79: Developing; monitor progress.
- 40–59: Support may be beneficial.
- Below 40: Priority for faculty review.

These bands must be configurable and must not be presented as validated probabilities of success.

# 15. Artificial Intelligence and Machine Learning

Build a genuine ML pipeline, not randomly generated predictions or hardcoded AI insights.

## 15.1 Academic Performance Prediction

Predict a clearly defined future outcome, such as:
- Next examination performance.
- Future academic percentage.
- Probability of falling below an academic threshold.
- Potential backlog risk where suitable historical labels exist.

Possible features:
- Previous examination marks.
- MID-1 and MID-2 marks.
- Subject-wise performance.
- Attendance history.
- Previous semester results.
- Assignment completion.
- Relevant LMS activity.
- Relevant engagement and skills indicators.

Start with a suitable baseline such as linear regression or logistic regression. Evaluate Random Forest or gradient boosting when appropriate.

Select models using evaluation results and interpretability, not complexity alone.

## 15.2 Placement Readiness Prediction

Use available:
- Aptitude assessments.
- Coding assessments.
- Technical skills.
- Communication assessments.
- Soft-skill assessments.
- Mock interviews.
- Placement preparation activity.
- Historical placement outcomes where available and authorized.

Do not predict actual placement outcomes from academic marks alone without suitable validated training data.

## 15.3 Risk Identification

Support configurable categories:
- Low concern.
- Moderate concern.
- High concern.
- Insufficient data.

Distinguish a low predicted outcome from low confidence in a prediction.

## 15.4 Training and Evaluation

Implement:
- Data cleaning.
- Feature engineering.
- Train, validation, and test splits.
- Leakage prevention.
- Baseline models.
- Cross-validation where appropriate.
- Evaluation metrics.
- Model versioning.
- Prediction timestamps.
- Periodic retraining.
- Performance monitoring.

For regression, consider MAE and RMSE. For classification, consider precision, recall, F1-score, ROC-AUC, and PR-AUC where appropriate.

If the dataset is small, imbalanced, or lacks outcome labels, report those limitations and use an appropriate baseline or rule-based assessment until sufficient data is available.

## 15.5 Explainable Predictions

- Strongest contributing indicators.
- Relevant historical changes.
- Model version.
- Prediction date.
- Suggested support actions.

Use feature importance or SHAP where appropriate. Do not confuse model feature contributions with causal explanations.

Never claim that a student will fail or succeed with certainty.

## 15.6 AI Recommendations
